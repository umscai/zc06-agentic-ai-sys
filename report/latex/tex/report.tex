\section{Overview}
We developed an agentic workflow~\parencites{agentic_Plaat_2025}{agentic_Hughes04072025} to classify pre-detected anomalies in industrial telemetry into three distinct operational response classes. The core system goal is to automate incident triage by identifying failure modes, conducting root-cause analysis, recommending corrective actions, and routing incidents to the appropriate operational tier for execution.

Built using LangGraph~\parencite{langgraph_overview_2026}, the orchestration framework utilizes a single central Large Language Model (LLM)~\parencite{enwiki:LLM} acting as a ReAct (Reasoning and Acting) agent~\parencite{react} within the classifier node to manage workflow decisions.

\subsection{Monitored Telemetry Parameters}
The system evaluates four core telemetry parameters representative of critical industrial assets, such as a Multistage Centrifugal Water Pump~\parencite{enwiki:cent-pump}:
\begin{enumerate}[font=\large\color{red}]
	\item \textbf{Temperature (\texttt{temperature\_c}):} Monitored at bearings, lubrication loops, or process fluids to track thermal friction and cooling efficiency.
	\item \textbf{Vibration (\texttt{vibration\_hz}):} Tracks mechanical oscillations to detect shaft misalignment, rotor imbalance, or bearing degradation.
	\item \textbf{Pressure (\texttt{pressure\_psi}):} Measures internal suction, discharge, or hydraulic line pressures.
	\item \textbf{Power (\texttt{power\_kw}):} Tracks real-time electrical power consumption to evaluate motor load and overall efficiency.
\end{enumerate}


\section{System Architecture and Design}

\subsection{Workflow Graph}
The agentic system's execution flow is modeled as a directed orchestration graph shown in Fig.~\ref{fig:graph}.

\begin{figure}[!tbh]
	\centering
	\includegraphics[width=0.4\textwidth]{workflow-details.drawio}
	\captionsetup{justification=centering}
	\caption{Workflow Graph.}
	\label{fig:graph}
\end{figure}

The execution sequence follows a multi-stage routing pipeline:
\begin{enumerate}[font=\large\color{red}]
	\item \textbf{Anomaly Detector Node:} Telemetry data enters the anomaly detector node and is logged to the telemetry database. If no anomaly is detected, the workflow terminates. If an anomaly is present, data is forwarded to the Classifier Agent.
	\item \textbf{Classifier Agent Node:} Operates as a ReAct agent using few-shot prompting~\parencite{ibm:fewshot} with clearly defined response classes. Context is enriched using the 3 most recent anomaly records retrieved from Long-Term Memory (LTM)~\parencites{ibm:agent-mem}{mlm:agent-mem}. The agent utilizes a single tool to fetch standardized severity bands for the current asset.
	\item \textbf{\texttt{CLASS\_0} Node:} Executes immediate asset shutdown protocols for critical safety hazards.
	\item \textbf{\texttt{CLASS\_1} Node:} Triggers automated control adjustments (e.g., via Variable Frequency Drive) for controllable process drifts.
	\item \textbf{\texttt{CLASS\_2} Node:} Escalate complex or unhandled anomalies by generating a comprehensive report for an on-site engineer.
	\item \textbf{LTM Update Node:} Updates the Long-Term Memory database with event details across all anomaly paths.
\end{enumerate}

\subsection{Data Storage and Persistence Architecture}
To maintain zero external deployment overhead while preserving operational isolation, the system employs three light-weight SQLite databases:
\begin{itemize}
	\item \textbf{Telemetry Database:} Stores continuous time-series logging of all incoming asset telemetry.
	\item \textbf{Short-Term Memory (STM) Checkpoint Store:} Captures full state checkpoints for offline auditing, system analytics, and performance tracking.
	\item \textbf{Long-Term Memory (LTM) Store:} Maintains a historical record of past anomaly events and resolutions per asset to provide historical context to the agent.
	\item \textbf{System Logging:} The system logs (error, debug, warning, info) are saved in \textbf{JSONL} format for easy offline parsing.
\end{itemize}
\textit{Please see sample of log and databases in the notebook.}


\subsection{Simplified Domain Grounding via Severity Bands}
While a production system could integrate Retrieval-Augmented Generation (RAG)~\parencite{enwiki:rag} against technical manuals, this implementation uses a deterministic threshold tool to convert raw numerical anomalies into standardized severity bands (\textit{Critically Low, Low, Normal, High, Critically High}), as shown in Fig.~\ref{fig:sev-band}.

\begin{figure}[!tbh]
	\centering
	\includegraphics[width=0.8\textwidth]{severity_bands.drawio}
	\captionsetup{justification=centering}
	\caption{Severity Bands.}
	\label{fig:sev-band}
\end{figure}

Bypassing raw statistical metrics (e.g., standard deviations and means) inside the LLM prompt prevents hallucination and reasoning errors. This abstraction aligns with practical engineering realities where a deviation of $10\sigma$ might represent a minor operational shift in one parameter but an immediate catastrophic failure in another.


\section{Decision Logic and Behavior}

\subsection{Anomaly Detection Logic}
Rather than relying on complex machine learning models, the anomaly detection node utilizes a transparent statistical rule set defined around baseline Gaussian distributions:
\begin{itemize}
	\item The full normal operating range spans \textcolor{ForestGreen}{$\pm 3\sigma$} centered around the mean.	
	\item An anomaly is flagged whenever any metric exceeds \textcolor{red}{$\pm 4\sigma$}.
	\item The ranges $[-4\sigma, -3\sigma]$ and $[+3\sigma, +4\sigma]$ serve as operational tolerance buffers prior to reporting an anomaly.
\end{itemize}

\subsection{Incident Severity Classification}
Once an anomaly is flagged, the central classifier agent categorizes the incident into one of three operational classes:
\begin{enumerate}[font=\large\color{red}]\setcounter{enumi}{-1}
	\item \textbf{\texttt{CLASS\_0} (Immediate Shutdown):} Triggered by severe threshold breaches (Critically High) on any dangerous parameter (temperature, pressure, or vibration) requiring instant asset shutdown to prevent catastrophic damage.
	\item \textbf{\texttt{CLASS\_1} (Automated Control):} Triggered by minor single-parameter operational stress or controllable process drift solvable via automated actuators (e.g., VFD).
	\item \textbf{\texttt{CLASS\_2} (Escalate to Onsite Engineer):} Triggered by physical degradation or complex multi-telemetry anomalies requiring physical inspection, maintenance, or manual intervention.
\end{enumerate}


\section{Safety, Reliability, and Transparency}

\subsection{Context Window Control and Latency Optimization}
Response latency is critical in industrial automation. To minimize inference delay, LTM access is kept outside the agent's tool execution loop; instead, relevant LTM context (the last 3 historical anomalies) is directly pre-loaded into the prompt before invocation.

Furthermore, because state checkpoints in STM are reserved strictly for offline auditing and analytics, input context lengths remain deterministic. Complex context management techniques—such as sliding-window truncation or message summarization—are unnecessary, preventing context drop and ensuring consistent reasoning across runs.

\subsection{LTM-Driven Behavioral Adaptation and Inconsistencies}
To assess the impact of Long-Term Memory, a \texttt{CLASS\_1} candidate scenario was evaluated under different LTM states:
\begin{itemize}
	\item \textbf{Without LTM:} The agent consistently routed the event to \texttt{CLASS\_1} for automated adjustment (Fig.~\ref{fig:class1-no-ltm}).
	\item \textbf{With LTM (Identical Past Failures Loaded):} Upon observing in LTM that prior automated adjustments had failed to clear the anomaly, the agent adapted its behavior and escalated the event to \texttt{CLASS\_2} (Fig.~\ref{fig:class1-ltm}).
	\item \textbf{Repeated Run After Time Delay:} In subsequent runs, the agent attempted an automated control intervention (\texttt{CLASS\_1}) once before re-escalating to \texttt{CLASS\_2} on the next occurrence (Fig.~\ref{fig:class1-ltm-again}).
\end{itemize}

While this shift demonstrates adaptive decision-making (giving automated control a secondary trial before escalating), it also highlights potential non-deterministic reasoning in LLM-based controllers.

\section{Ethical and Responsible Use Considerations}
Automating control decisions and emergency shutdowns in industrial physical infrastructure introduces significant operational risks. Granting autonomous agents direct execution authority over \texttt{CLASS\_0} emergency shutdowns poses a trade-off:
\begin{itemize}
	\item \textbf{Safety vs. Financial Cost:} An automated emergency shutdown prevents catastrophic physical failure, protecting personnel and infrastructure. However, false positives cause expensive, unnecessary production halts.
	\item \textbf{Accountability and Delays:} Requiring a Human-in-the-Loop (HITL) for critical shutdowns mitigates false-positive costs but introduces latency that may lead to physical destruction during fast-moving failure modes.
\end{itemize}


\section{Future Improvements}
To address present system limitations, future development will target the following areas:
\begin{enumerate}
	\item \textbf{Machine Learning Anomaly Detection:} Replace rule-based deviation bounds with trained machine learning models fitted on historical industrial telemetry.
	\item \textbf{Generative Data Pipelines:} Integrate Generative AI models to synthesize diverse normal and rare failure-mode telemetry for robust benchmark testing.
	\item \textbf{Expanded Actuator Integration:} Extend control capability beyond Variable Frequency Drives (VFDs) to include actuators like bypass and recirculation valves.
	\item \textbf{Closed-Loop Simulation:} Implement continuous closed-loop feedback environments to dynamically evaluate asset recovery following agent-initiated control adjustments.
	\item \textbf{Configurable Safety Guards:} Incorporate optional Human-in-the-Loop approval nodes for emergency shutdowns based on facility-specific risk profiles.
\end{enumerate}% apa does not include ref and appx in TOC we forced it
